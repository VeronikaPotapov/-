# AGENTS.md

Этот файл — постоянно развивающаяся база знаний проекта. Его нужно обновлять, когда меняется функциональность, архитектура, документация, проектные правила или устойчивые предпочтения пользователя.

## Краткое описание проекта

Проект — локальный MVP веб-приложения «Личный кабинет РП» / «Операционный план РП».

Назначение приложения — помочь руководителю проекта работать с операционным планом:

- создавать и открывать проекты;
- вести локальный профиль пользователя;
- видеть операционные действия по неделе, месяцу, текущей стадии и общему списку;
- отмечать выполнение действий;
- вести комментарии и плановые даты по действиям;
- видеть прогресс проекта и раздела;
- управлять участниками и правами доступа в рамках локальной MVP-модели;
- администрировать локальный справочник операционных действий;
- смотреть сводный экран «Мой план на неделю» по доступным проектам.

MVP работает локально: данные хранятся в браузере через `localStorage`. Сервер, база данных, настоящая авторизация и сборщик не используются.

## Технологии и архитектурные принципы

- Используются обычные `HTML`, `CSS` и `JavaScript`.
- Нет `React`, `Vite`, сборщика, backend, серверной базы данных и пакетного менеджера.
- Приложение можно открыть напрямую через `index.html` или через Live Server в VS Code.
- Совместимость с GitHub Pages должна сохраняться.
- Состояние хранится в `localStorage`.
- Рендеринг выполняется вручную в `app.js` через шаблонные строки и центральную функцию `render()`.
- После каждого рендера события заново навешиваются через `bindEvents()`.
- Основные ключи `localStorage`:
  - `rpNavigatorState` — профиль пользователя, проекты, участники, статусы действий, комментарии, даты;
  - `rpNavigatorActions` — пользовательская версия справочника операционных действий.
- Дефолтные действия хранятся в `defaultOperationalActions`.
- Рабочий список действий нельзя брать напрямую из дефолтного массива. Нужно использовать функции:
  - `getAllOperationalActions()` — все действия для админки;
  - `getActiveOperationalActions()` — только активные действия для экранов РП.

Главный архитектурный принцип: сохранять MVP простым, локальным и пригодным для статического размещения.

## Структура проекта

Проект сейчас имеет плоскую структуру:

- `index.html`
  - Статическая HTML-оболочка приложения.
  - Подключает `styles.css` и `app.js`.
  - Содержит верхний header и `<main id="app"></main>`, куда JavaScript рендерит интерфейс.

- `styles.css`
  - Все стили приложения.
  - Содержит стили раскладки, карточек, кнопок, форм, прогресс-баров, тёмной темы, адаптивности, админки и карточек действий.

- `app.js`
  - Основная логика приложения.
  - Содержит константы, дефолтный справочник действий, загрузку/сохранение состояния, рендер-функции, обработчики событий, логику проектов, профиля, админки, расчёта прогресса, фильтров, доступа и утилиты.

- `README.md`
  - Пользовательская документация проекта.
  - Описывает назначение MVP, запуск, реализованные функции, ограничения и возможное развитие.
  - Важно: если русский текст в терминале отображается некорректно, перед правками нужно проверить кодировку и сохранить читаемый русский текст.

- `AGENTS.md`
  - Техническая база знаний для дальнейшей разработки.
  - Должен обновляться после значимых изменений.

Отдельных каталогов с ADR, архитектурными заметками или проектными решениями сейчас нет.

## Правила разработки и кодирования

- Сохранять приложение статическим и совместимым с GitHub Pages.
- Не добавлять backend, сервер, базу данных, настоящую авторизацию, сборщик, `React`, `Vite` или пакетный менеджер без явного запроса пользователя.
- Делать изменения точечно, без крупных переписываний без необходимости.
- Не менять ключи `localStorage` и структуру данных без согласованной миграции.
- Не ломать:
  - профиль пользователя;
  - создание проекта;
  - список «Мои проекты»;
  - открытие проекта;
  - удаление проекта;
  - участников и права доступа;
  - статусы действий;
  - комментарии;
  - плановые даты;
  - расчёт прогресса;
  - переключатель «Выполнено / Не выполнено»;
  - админку действий;
  - импорт/экспорт справочника действий;
  - статическое размещение на GitHub Pages.
- Не менять `id` существующих действий в `defaultOperationalActions`: по ним хранятся статусы в проектах.
- Для экранов РП использовать только активные действия: `isActive !== false`.
- Для админки показывать все действия: активные и отключённые.
- Новые поля действия обязательно нормализовать в `normalizeAction()`.
- При изменении структуры состояния проекта обновлять `normalizeState()` и документировать миграцию.
- Все динамические пользовательские значения в HTML-шаблонах экранировать через `escapeHtml()`.
- Сохранять текущий подход к рендерингу через функции с шаблонными строками.
- Обработчики событий держать в `bindEvents()`, если нет веской причины сделать иначе.
- Не делать commit, push или деплой без прямой просьбы пользователя. Можно только рекомендовать это сделать.

## Правила проектирования новых функций

- Новые функции сначала проектировать в рамках текущей локальной MVP-модели.
- Для MVP предпочитать имитацию через `localStorage`, а не реальный backend.
- Разделять дефолтные данные и пользовательские изменения.
- Сохранять старые проекты, статусы и комментарии при развитии функциональности.
- Админские функции показывать только подходящей роли. Сейчас доступ в админку определяется ролью `Администратор департамента`.
- При добавлении фильтров, расчётов и сводок учитывать:
  - стадию проекта;
  - тип проекта;
  - активность действия;
  - статус действия внутри конкретного проекта.
- Пользовательский интерфейс должен оставаться продуктовым и понятным. Технические детали лучше прятать во вторичные или раскрывающиеся блоки.
- Для дизайн-задач преимущественно работать в `styles.css`.
- `app.js` и `index.html` менять только если нужны новые классы, структура или элементы интерфейса.
- Текущий визуальный ориентир: тёмная сине-графитовая палитра, деловой технологичный стиль, glassmorphism-карточки, бирюзовые акценты, хороший контраст текста.
- При работе с Figma создавать редактируемые слои, а не просто вставлять скриншот.

## Требования к тестированию

Автоматических тестов в проекте пока нет.

После значимых изменений вручную проверять:

- приложение открывается через `index.html` или Live Server;
- нет пустого экрана и критических ошибок загрузки;
- профиль создаётся и редактируется;
- проект создаётся, открывается, редактируется и удаляется;
- демо-проект работает;
- «Мои проекты» показывает только доступные проекты;
- «Мой план на неделю» открывается и возвращает назад к проектам;
- действия отображаются по неделе, месяцу, стадии и в общем списке;
- фильтры в «Все действия» работают;
- переключатель «Выполнено / Не выполнено» сохраняет статус и обновляет прогресс;
- комментарии сохраняются;
- плановые даты сохраняются;
- быстрый выбор стадии проекта работает;
- участники и права доступа не сломаны, если затрагивалась эта зона;
- роль администратора открывает «Админку действий»;
- в админке можно добавить, отредактировать, отключить, удалить, импортировать, экспортировать и сбросить действия;
- отключённые действия не появляются на экранах РП;
- сброс справочника удаляет только `rpNavigatorActions`;
- «Очистить данные» удаляет только `rpNavigatorState`, если специально не согласовано иное;
- адаптивность не ломается на узком экране.

Перед завершением изменений по возможности запускать:

- `git diff --check`;
- проверку открытия страницы в браузере или через Live Server;
- headless/smoke-проверку браузером, если доступна.

## User Preferences

- Пользователь предпочитает сначала согласовать план перед крупными или рискованными изменениями.
- После согласования плана можно переходить к реализации без лишнего ожидания.
- Не делать commit, push, публикацию на GitHub Pages или деплой без явной просьбы пользователя.
- Можно рекомендовать отправить изменения на GitHub, но нельзя делать это автоматически.
- Если задача визуальная, бизнес-логику не трогать.
- Если пользователь говорит «только styles.css», нельзя менять HTML или JS.
- Пользователь ценит точечные изменения и сохранение уже работающих сценариев.
- Пользователь предпочитает продуктовый, простой интерфейс вместо перегруженного техническими таблицами экрана.
- Если пользователь просит «почти как на скрине», нужно делать максимально близко к референсу, а не свободную интерпретацию.
- Для Figma нужны редактируемые слои, а не вставленная картинка.
- Важно сохранять текущие названия и элементы продукта, например «Личный кабинет РП» и «Мой план на неделю».
- Документация и база знаний должны развиваться вместе с проектом.

## Project Learnings

- Проект начинался как локальный MVP операционного навигатора для руководителя проекта.
- Текущее название в интерфейсе — «Личный кабинет РП».
- «Операционный план РП» используется как контекст продукта и проекта.
- Основное состояние приложения хранится в `rpNavigatorState`.
- Пользовательский справочник действий хранится в `rpNavigatorActions`.
- ID дефолтных действий нельзя менять, потому что статусы проектов ссылаются на `actionId`.
- Правило видимости действий для РП: `isActive !== false`.
- Админка должна показывать и активные, и отключённые действия.
- Действия могут быть привязаны к `projectType`.
- При создании проекта показывается превью количества активных действий для выбранного типа проекта.
- Текущие типы проекта: «Внедрение», «Поддержка», «Внутренний проект», «Иной тип».
- Доступ к проекту имитируется локально через владельца и участников.
- Настоящей авторизации нет.
- Доступ в админку имитируется через роль профиля «Администратор департамента».
- Экран «Мой план на неделю» — отдельный локальный режим интерфейса, а не маршрут.
- В приложении нет маршрутизации: режимы управляются переменными состояния и повторным рендером.
- `README.md` — основная найденная пользовательская документация.
- Использовавшийся Figma-файл: `https://www.figma.com/design/Y9DYWIuNyjnA1PJvIPN5rv/Untitled`.
- Figma-макеты должны отражать текущее состояние приложения, а не только раннюю концепцию.
